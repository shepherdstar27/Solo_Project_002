### 게임 소개

트럭을 몰고 도로를 달리며 길 위의 오브젝트를 들이받아 흡수하고, 흡수한 대상을 아군 유닛으로 변환해 레인 디펜스 전투를 치르는 게임입니다. 주행으로 모은 자원이 곧 전투 전력이 되도록 두 파트를 하나의 흐름으로 연결했습니다.

한 판은 60초이며, 코스 끝의 보스와 충돌하면 격돌 시퀀스로 넘어갑니다. 연타로 게이지를 채워 보스를 밀어내면 그 보스가 아군으로 전향해 적 본진까지 진격하고, 엔딩 컷과 채점표가 이어집니다.

### 이번 프로젝트에서 집중한 것

JSON 데이터 드리븐 구조와 UI 매니저 등 앞선 프로젝트에서 정립한 기반은 그대로 가져왔습니다. 대신 이번에는 그동안 다루지 않았던 **에디터 확장, 물리 기반 조작, 비동기 리소스 로딩**에 시간을 썼습니다.

전투 로직은 `MonoBehaviour`를 쓰지 않고 순수 C# 클래스로 짜서, 화면 표시를 담당하는 뷰와 이벤트로만 연결했습니다.

### 데이터 파이프라인

기획 수치는 모두 `Assets/Resources/JsonOutput/` 아래 JSON 테이블에 있고, 코드에는 상수를 두지 않았습니다.

- 각 테이블은 `GameDataBase`를 상속한 `[Serializable]` 클래스와 1:1로 대응합니다.
- JSON은 최상위 배열로 두고, 로드 시 `{"datas": ... }` 형태로 감싸 `JsonUtility`로 역직렬화합니다. `JsonUtility`가 최상위 배열을 직접 읽지 못하는 제약을 우회하기 위한 처리입니다.
- 조회는 `GameDataManager.Instance.GetData<T>(id)` 제네릭 창구 하나로 통일했습니다. 테이블을 추가할 때 `LoadAllData()`에 한 줄만 더하면 됩니다.
- enum은 JSON에 문자열로 저장하고 코드에서 변환합니다. 표에서 값을 눈으로 읽을 수 있도록 한 선택입니다.
- 리스트형 필드는 쉼표로 구분한 문자열(`"Monster_01,Monster_02"`)로 저장하고 파서를 통해 읽습니다.

현재 테이블은 티어, 유닛, 몬스터, 웨이브, 스테이지, 업그레이드, 흡수 대상, 스폰 구역 8종입니다.

## 2장 — 에디터 맵 생성기

### 기능 설명

도로와 가드레일, 도로변 오브젝트를 버튼 한 번으로 생성하는 에디터 툴입니다. `Tools/맵 생성기` 메뉴에서 열고, 레이아웃 에셋을 지정한 뒤 생성 버튼을 누르면 맵이 만들어집니다.

레이아웃 에셋에는 구간별로 타일 수, 폭, 하강 높이, 타일당 회전각, 이전 구간과의 연결 여부를 지정합니다. 구간을 연결로 두면 앞 구간이 끝난 지점과 방위를 그대로 물려받아, 좌표를 손으로 맞출 필요가 없습니다.

※ GIF: 버튼을 누르면 도로가 생성되는 장면

### 설계 포인트

**타일 배치에서 연속 메시로.** 도로를 타일 프리팹으로 이어 붙이면 곡선 구간마다 이음새가 벌어집니다. 폭 `W`인 도로가 타일마다 `θ`만큼 꺾이면 바깥쪽에 `(W/2)·tan(θ)`의 틈이 생기는데, 폭 40m에 타일당 4°면 1.4m입니다. 처음에는 타일을 서로 겹치도록 늘려 메우는 방식으로 대응했지만, 구간 경계의 꺾임까지 계산에 넣어야 해서 예외가 계속 나왔습니다. 결국 타일을 붙이는 대신 **경로를 따라 단면을 훑어 하나의 연속된 메시로 생성**하도록 바꿨습니다. 이 방식은 이음새와 겹침이 구조적으로 생기지 않습니다.

**텍스처 반복 기준.** UV의 V를 구간 길이로 정규화하면 짧은 구간과 긴 구간의 무늬 간격이 달라집니다. 그래서 **시작점부터의 누적 이동거리를 텍스처 길이로 나눈 값**을 V로 썼습니다. 구간 길이와 무관하게 지정한 미터마다 무늬가 한 번 반복됩니다.

**가드레일의 수직 유지.** 단면 좌표를 도로의 로컬 상방으로 밀어 올리면 내리막에서 가드레일이 같이 기웁니다. 높이 방향만 월드 기준 `Vector3.up`으로 계산해 경사 구간에서도 똑바로 서게 했습니다.

### 구현 방식 요약

1. 레이아웃 에셋의 구간 정보를 읽어 경로를 생성합니다. 위치와 방위를 들고 한 스텝씩 전진하며 점을 찍는 방식으로, 곡선 구간은 스텝마다 방위를 조금씩 돌립니다.
2. 경로의 각 지점마다 단면 좌표를 배치해 정점 링을 만듭니다. 단면만 바꾸면 도로와 좌우 가드레일을 같은 코드로 생성할 수 있습니다.
3. 인접한 두 링을 사각형으로 이어 삼각형을 구성합니다.
4. 생성한 메시를 에셋으로 저장합니다. 긴 코스에서는 정점 수가 65,535개를 넘기므로 인덱스 포맷을 32비트로 지정했습니다. ※ 실제 코스 기준 정점 수를 확인해 적으면 설득력이 올라갑니다.

도로변 오브젝트는 코스 진행률(0~1) 구간으로 배치합니다. 처음에는 월드 좌표 범위로 지정했는데, 코스가 곡선이 되면서 좌표 범위를 벗어난 구간에는 오브젝트가 하나도 놓이지 않는 문제가 있었습니다. 배치에 실패하면 경고를 남기도록 해 이런 상황을 조용히 넘기지 않게 했습니다.

### 왜 만들었나

맵을 손으로 배치하는 일이 반복 작업이었고, 코스를 한 번 수정할 때마다 도로 전체를 다시 맞춰야 했습니다. 툴을 만드는 데 든 시간보다 이후 절약한 시간이 더 컸습니다. 특히 밸런싱 과정에서 코스 길이를 여러 번 바꿨는데, 툴이 없었다면 그때마다 수작업이었을 것입니다.

## 3장 — 트럭 주행과 오브젝트 흡수

### 기능 설명

`WheelCollider` 기반으로 트럭을 조작하고, 주행 중 부딪힌 오브젝트를 흡수해 콤보와 점수로 연결합니다. 누적 점수가 기준을 넘으면 티어가 오르고, 티어가 오르면 더 큰 대상을 흡수할 수 있습니다.

### 설계 포인트

**전복과 조향.** 트럭이 커브에서 자주 전복돼, 무게중심을 차체 아래로 내리고 속도에 비례한 다운포스를 주어 접지를 유지했습니다. 고속에서 조향이 과민해지는 문제는 속도가 오를수록 최대 조향각을 줄이는 방식으로 잡았습니다.

**흡수 중 감속 제거.** 흡수는 0.2초 동안 대상이 빨려 들어오는 연출로 처리하는데, 이 사이에 트럭이 대상과 물리 충돌해 속도가 깎였습니다. 처음에는 대상 루트의 콜라이더만 껐지만 자식에 달린 모델 콜라이더가 남아 있었고, 흡수 판정보다 물리 충돌이 먼저 일어나는 순서 문제도 있었습니다. 최종적으로 세 가지를 함께 적용했습니다.

- 자식까지 포함한 모든 콜라이더를 비활성화
- 대상 Rigidbody의 `detectCollisions`를 끄기
- 그럼에도 이미 들어온 충격량은 직전 프레임 속도를 되돌려 상쇄

**비동기 리소스 로딩.** 프리팹 로딩은 Addressables와 UniTask로 비동기 처리해, 스테이지 구성 중 화면이 멈추지 않게 했습니다. 이전 개인 프로젝트에서는 리소스를 동기 방식으로 불러왔는데, 이번에 바꾼 부분입니다.

### 오브젝트 풀링에 대해

흡수 대상은 한 맵에 수백 개가 놓이므로 키 단위 오브젝트 풀(`ObjectPoolManager`)을 만들어 두었습니다. 다만 **최종적으로는 이 경로를 쓰지 않습니다.** 2장의 에디터 툴이 맵 오브젝트를 미리 씬에 배치하는 방식으로 바뀌면서 런타임 스폰이 필요 없어졌고, 런타임에 풀을 생성하던 `MapSpawner` 호출은 주석 처리한 상태입니다. 풀이 없는 키로 반납이 들어오면 그대로 파괴되므로, 현재 빌드에서 흡수된 오브젝트는 파괴됩니다.

에디터에서 미리 배치하면 로딩 중 생성 비용이 사라지고 배치 결과를 눈으로 확인·수정할 수 있어 이쪽을 택했습니다. 대신 오브젝트가 씬에 상주하므로 메모리 사용은 늘어납니다. 코스가 더 길어지면 구간 단위 스트리밍이 필요해질 텐데, 그때는 만들어 둔 풀을 다시 쓰게 될 것입니다.

## 4장 — 유닛 변환과 레인 디펜스

### 기능 설명

주행 중 흡수한 대상을 아군 유닛으로 변환해 화면 오른쪽 레인 전투에 투입합니다. 웨이브로 내려오는 적을 막아내고, 코스 끝에서는 보스와 격돌 시퀀스를 치릅니다.

### 설계 포인트

**전투 로직과 화면의 분리.** 전투 규칙은 `MonoBehaviour`가 아닌 순수 C# 클래스(`LaneSimulation`)에 있습니다. 유닛 생성·제거·본진 도달은 이벤트로 알리고, 화면을 그리는 `DefenseStripView`가 이를 구독합니다. 전투 규칙을 화면과 떼어놓아야 값을 바꿔가며 확인하기 쉽다고 판단했습니다. 실제로 밸런싱은 대부분 JSON 수정과 인스펙터 값 조정만으로 처리했습니다.

**대형 자동 구성.** 유닛은 배치 타입에 따라 소환 위치를 다르게 잡습니다. 구조물은 최전선(0.45), 근접은 전방(0.15), 원거리는 후방(0.05)에 서도록 해 별도 지시 없이도 대형이 갖춰지게 했습니다.

**타겟 재계산 주기.** 타겟 탐색은 아군 × 적 전수 비교라 개체 수에 대해 제곱으로 늘어납니다. 웨이브를 한꺼번에 스폰하도록 바꾸면서 한 화면에 100개 이상이 공존하게 돼, 타겟을 매 프레임이 아니라 0.2초 간격으로만 다시 찾도록 했습니다. 다만 지금 노리던 대상이 죽었거나 목록에서 빠진 경우에는 간격과 무관하게 즉시 다시 찾습니다. 죽은 대상을 최대 0.2초 동안 계속 때리는 것을 막기 위해서입니다.

**보스 격돌.** 격돌은 상태를 여섯 단계(`None → Clash → Push → March → Cut → Ending`)로 나눠 순서를 고정했습니다. 필요한 연타 수는 충돌 속도와 티어로 계산한 위력에 따라 줄어들되 최소치 아래로는 내려가지 않게 해, 잘 모았어도 마지막에 아무것도 하지 않고 끝나지 않도록 했습니다.

### 구현 방식 요약

1. 흡수 대상의 크기 값을 티어 테이블과 대조해 유닛 ID로 변환합니다.
2. 유닛 테이블에서 체력·공격력·공격 간격·사거리·이동 속도·수명을 읽어 개체를 생성합니다.
3. 매 프레임 시뮬레이션을 갱신합니다. 0.2초 간격으로 타겟을 다시 찾고, 사거리 안이면 정지 후 공격, 아니면 이동합니다.
4. 적이 게이트에 닿으면 왕성 체력을 깎습니다. 왕성이 무너지거나 제한 시간이 지나면 실패, 보스 격돌에 성공하면 클리어입니다.
5. 전향한 보스는 전선을 넘어 적 본진까지 올라가며, 도달 시점에 엔딩 컷과 채점표로 이어집니다.

### 채점

한 판의 결과를 아홉 항목으로 나눠 채점합니다. 흡수 점수, 흡수 횟수, 최대 콤보, 전송 유닛 수, 충돌 속도, 최종 티어, 왕성 잔여 체력, 도달 시간, 격돌 연타. 주행과 전투 양쪽의 성과가 모두 최종 점수에 반영되도록 항목을 나눴습니다.

## 5장 — 개발 중 이슈

### 이슈 1 — 비동기 예외가 시퀀스를 통째로 삼킨 문제

**증상.** 보스와 충돌하는 순간 게임이 멈춘 것처럼 보였습니다. 크래시도 에러도 없이 트럭은 서 있고 화면은 그대로였습니다.

**원인.** `Addressables.LoadAssetAsync`는 등록되지 않은 주소를 넘기면 null을 돌려주는 게 아니라 `InvalidKeyException`을 던집니다. 이 호출이 `.Forget()`으로 띄운 UniTask 안에 있었기 때문에, 예외가 어디에도 잡히지 않고 그 태스크만 조용히 중단됐습니다. 그 결과 `await` 뒷부분이 통째로 실행되지 않았습니다. 상태 전환도, 세션 재개도, 입력 잠금 해제도 전부 그 뒤에 있었기 때문에, 트럭은 `isKinematic`인 채 세션은 일시정지, 입력은 잠긴 상태로 남았습니다.

**해결.** 로드 호출을 try/catch로 감싸 실패를 로그로 드러내고 null을 돌려주도록 바꿨습니다. 호출하는 쪽은 null을 받으면 화면 없이 시퀀스만 진행하도록 해, UI 프리팹이 준비되기 전에도 흐름을 확인할 수 있게 했습니다.

**배운 점.** 비동기 경로에서 예외를 삼키면 크래시가 아니라 **멈춤**으로 나타납니다. 스택 트레이스가 없으니 증상이 보이는 지점과 원인 지점이 완전히 어긋나고, 그래서 처음에는 격돌 로직 쪽을 한참 들여다봤습니다. 실제 원인은 그 위에 있었습니다. 이후로는 `.Forget()`으로 띄우는 태스크에 예외 처리를 빠뜨리지 않았습니다.

### 이슈 2 — 재시작하면 트럭이 두 대 생성되던 문제

**증상.** 결과창에서 다시하기를 누르면 트럭이 튕겨져 날아갔습니다.

**원인.** 로그를 보니 스테이지 로드 로그가 두 번씩 찍혀 있었습니다. 다시하기는 씬을 다시 로드하는데, `UIManager`가 `DontDestroyOnLoad`라 캐시된 메인 메뉴 UI 인스턴스가 씬 리로드 후에도 살아남습니다. 반면 부트스트랩 객체는 씬과 함께 파괴되고 새로 생성됩니다. 이전 부트스트랩이 걸어둔 시작 버튼 이벤트 구독은 살아남은 UI 쪽에 그대로 남아 있었고, 새 부트스트랩이 같은 이벤트에 한 번 더 구독하면서 핸들러가 두 개가 됐습니다. 버튼 한 번에 스테이지가 두 번 로드되고, 같은 자리에 겹쳐 생성된 트럭 두 대가 서로를 밀어내며 날아간 것입니다.

**해결.** 부트스트랩이 UI 참조를 들고 있다가 `OnDestroy`에서 구독을 해제하도록 하고, 구독 전에 한 번 해제하는 처리도 함께 넣었습니다. 스테이지 로더에는 중복 로드를 막는 플래그를 두어, 다른 경로로 두 번 불려도 트럭이 두 대 생기지 않도록 이중으로 막았습니다.

**배운 점.** `DontDestroyOnLoad` 객체의 수명은 씬 수명과 다릅니다. 그리고 C# 이벤트 구독은 대상 `MonoBehaviour`가 파괴돼도 자동으로 끊기지 않습니다. 씬을 넘나드는 객체를 만들 때는 구독 해제 지점을 함께 설계해야 한다는 것을 배웠습니다.

### 이슈 3 — 전투가 진행되지 않고 멈춘 문제

**증상.** 아군과 적이 서로를 바라본 채 아무 일도 일어나지 않고, 제한 시간이 지나서야 판이 끝났습니다.

**원인.** 아군과 적이 같은 정지 조건을 쓰고 있었습니다. 아군은 정해진 전선(0.5)까지만 전진하는데, 사거리가 0.25인 원거리 적은 그보다 위인 0.75에서 이미 사거리 안에 들어왔다고 판단해 멈춰 섰습니다. 아군 근접 유닛의 사거리는 0.06이므로 전선에서 닿을 수 있는 최대 거리는 0.56입니다. 결과적으로 적의 공격은 닿지만 아군의 공격은 닿지 않는 거리에서 양쪽이 정지했습니다. 개별 유닛의 사거리 값은 모두 정상이었고, 문제는 두 진영의 정지 기준을 하나로 묶어둔 설계에 있었습니다.

**해결.** 아군이 넘지 않는 전선과, 적이 사거리와 무관하게 반드시 내려와야 하는 정지선을 별개의 값으로 분리했습니다. 두 선의 간격을 아군 최소 사거리 안쪽으로 잡아, 적이 어디서 멈추든 아군의 공격이 닿도록 보장했습니다. 두 값은 인스펙터로 빼서 조정할 수 있게 했습니다.

**배운 점.** 값이 아니라 규칙을 의심해야 하는 경우가 있습니다. 사거리와 이동 속도를 아무리 조정해도 해결되지 않았던 이유는, 두 진영이 같은 기준을 공유한다는 전제 자체가 잘못이었기 때문입니다.

## 6장 — 회고와 남은 과제

### 회고

이번 프로젝트에서 가장 크게 남은 것은 **도구를 먼저 만드는 판단**이었습니다. 맵 생성기를 만들 때는 게임 자체의 진도가 멈추는 것 같아 망설였는데, 이후 코스 길이와 오브젝트 배치를 여러 번 갈아엎으면서 그 결정이 시간을 되돌려 줬습니다.

반대로 아쉬운 것은 **연출을 뒤로 미룬 것**입니다. 시스템을 먼저 다 붙이고 UI 프리팹과 이미지를 마지막에 넣으려다 보니, 흐름은 동작하는데 화면이 비어 있는 기간이 길었습니다. 최소한의 표시라도 초반에 붙여 두는 편이 검증에도 유리했을 것 같습니다.

### 남은 과제

- 스테이지 데이터 확장과 밸런싱 (현재 1스테이지 기준으로만 조정)
- 주행 파트와 전투 파트 사이 전환 연출 보강
- 맵 생성기의 오브젝트 배치 규칙 다듬기 (겹침 회피와 밀도 조절)
- 레인 유닛의 상태별 애니메이션 전환 (현재는 대기 동작만 재생)
- 개체 간 겹침 방지 처리 활성화 (구현은 되어 있으나 성능 부담으로 미적용)
